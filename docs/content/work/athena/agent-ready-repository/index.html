The operating premise

A repository should help work reach a trustworthy finish

In April 2026 I audited the repository against published harness-engineering practice (the essays from Martin Fowler’s site and OpenAI on keeping large codebases legible to coding agents) and turned the gaps into a ticket series. That series became what this page describes: deterministic self-tests, diff-aware review, runtime behavior scenarios, a quality scorecard, and a janitor that repairs drift.

AI agents can search a large repository quickly, but search is not understanding. Athena begins with generated package maps, route and entry-point guides, validation maps, and a repository graph built with Graphify, so a contributor grounds the problem in the code and runtime before proposing a change.

Delivery infrastructure

The repository makes its boundaries legible

The harness starts with an explicit registry of active package surfaces. The registry feeds the generated maps; sensors compare those expectations against the live repository; review commands assemble the evidence that moves a local edit toward a reviewable release candidate.

Change-aware proof

The change declares what can prove it

Generated validation maps connect each package surface to the commands and behavior scenarios that can evaluate it. Review commands diff a branch against its base and use the maps to point at the missing proof, so no contributor reconstructs the strategy from memory.

Freshness checks are fail-closed. A repair command may regenerate maps or documentation, but repaired evidence never slides past review: the workflow stops so the changed artifacts are inspected and committed on purpose.

The vocabulary is the design. A recorded proof is reused only while its exact conditions hold; anything else reruns the gate and says why: stale, dirty, base_changed, validation_wiring_changed, generated_repaired. Evidence is invalidated by observed drift, not by suspicion.

End-to-end delivery

The work narrows while the evidence widens

Substantial Athena work moves through the same shape every time: understand what is actually true in the code and at runtime, write down what will prove the change, build it, put it through risk-selected review, ship it, check the live boundary.

The shape is not a checklist in a doc. It is encoded as skills the agents invoke, so a behavior change starts with a failing test and is not done at “PR open”: done is merged, closed, and reported. The tracker holds the work record, the repo holds the sensors, the skills hold the workflow.

The work narrows (problem, scope, units, one branch) and the evidence widens: tests first, then cross-layer checks, gates, and review lenses picked by risk. Those lenses are mostly agents reviewing other agents’ work; I choose the scope, set the risk posture, and decide whether the evidence earns a release. What gets approved is the exact bundle that ships (requirements, plan, diff, evidence), not a locally correct patch.

Findings become work. A fix produces new evidence, and the affected lenses look at the exact current artifact again. An edit after approval makes that approval stale. High-risk changes loop until every lens approves: unanimity before merge. Small ones do not get the full ceremony.

Progressive assurance

The checks get broader as the change moves outward

Each layer answers a question the one before it cannot: does the behavior work, do adjacent systems still agree, is the repository coherent, what did the implementation path miss, does the release candidate hold, does the deployed boundary behave.

Static checks are one sensor. Named behavior scenarios boot representative runtime paths and emit machine-readable [harness:behavior:report] lines (phase durations, matched signals) that an agent or a trend dashboard can parse. Production-facing work continues into deployed logs, state, and responses, so confidence is grounded in the environment that matters.

Learning compounds

The finish line improves the next starting point

Generated maps and solution notes are reviewable source artifacts. Substantial work leaves behind the problem, the solution, and the prevention pattern, so the next human or agent starts with more context than the last one had.

The loop is most visible when something escapes. When money inputs were caught saving display amounts where minor units belonged, the fix landed with a static audit that scans every money-entry boundary and fails validation on raw float parsing. Escaped failures become sensors the next contributor inherits. The gain is not more code per prompt, but gaps that are harder to carry forward unnoticed.

Candid limits

Agent-ready is not agent-autonomous

The harness increases legibility and raises the quality of available evidence. It does not give an agent complete understanding of the codebase, make runtime coverage exhaustive, make test coverage complete, or promise regression-free delivery.

  • Maps can become stale, which is why freshness checks block rather than assume.
  • Behavior scenarios exercise representative paths, not every production condition.
  • Validation output supports judgment; it does not replace product or engineering review.
  • Review depth is selected by risk; not every task takes the same path, and small changes can take a shorter one than cross-cutting or production-critical work.
  • Human reviewers remain responsible for scope, tradeoffs, evidence quality, and release decisions.

Evidence reviewed

The process is visible in the delivery artifacts

This account is grounded in what Athena work leaves behind: scope and proof defined before implementation, findings recorded against the integrated artifact, repository and release gates, live verification, and durable learning.

  • Requirements and plans that define scope, non-goals, risks, dependencies, and verification before implementation.
  • Integrated changes and the findings, fixes, and clearance produced by independent review lenses.
  • Repository gates, pull-request checks, deployment evidence, and verification at the live operating boundary.
  • Harness documentation, generated repository maps, behavior scenarios, review commands, and durable solution notes.
