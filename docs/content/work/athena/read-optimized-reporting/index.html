Read-optimized reporting

Why the reports workspace runs on one fact ledger and one pure fold, and why the dashboard costs a single document read.

The operating record

One workspace answers what the business actually did.

Athena is the operating system a solo owner runs a retail and service business on: point of sale, an online storefront, service work, inventory, cash controls, and a daily close. Each of those domains keeps its own authoritative records. The reports workspace is where those records become answers — an overview of net sales, gross profit, and trend; a day-by-day table with each day’s settlement status; and item performance down to a single SKU on a single day, with the transactions behind a number one click away.

The report layer is the backend machinery between the two. It turns domain events into those numbers and owns nothing else: it is derived by construction, rebuildable from the operational record at any time, and no operational workflow ever reads reporting to decide whether its own command succeeded. That one-way dependency is the boundary the whole design leans on. This page is about what the layer looked like when that machinery was built wrong, and how it was rebuilt.

The failure mode

A dashboard should not spend thousands of reads to say what today earned.

Athena’s first reporting layer stored one row per metric, and the cost was measured before the rewrite: 1,284 canonical facts across 64 operating days had fanned out into roughly 35,800 derived and audit rows — about 28 rows per fact. The overview read 340–440 documents per execution and re-ran on every applied fact, on the order of 6,000 to 19,000 reads a day to keep one dashboard current.

The unit of storage was wrong, so no amount of tuning could make the reads right.

The rebuild inverted the unit: a metric is a field on a day document, never a row. The same store now produces about 0.9 derived documents per fact, and the dashboard subscribes to exactly one document.

The shape of the layer

One ledger, one fold, four read models, seven queries.

The layer is deliberately not a reporting engine. There are no report definitions, no exporters, no query builder. There is an append-only fact ledger (reportFact), a pure function that folds one operating day (foldDay), derived documents shaped for exactly what the workspace renders, a dirty-day work queue, and a small set of read queries. Everything else on this page is a consequence of keeping that list short.

The frozen contract

The backend and the UI import the same shapes, or the build fails.

Every metric name, status, and result shape lives in one shared module, reportsContract.ts, imported by both the backend and the UI. A dashboard rendering a metric the backend stopped materializing is a compile error, not a blank panel. The module is declared frozen — changes escalate, they do not accrete — and a parity test walks the stored schemas at runtime to assert the contract and the tables agree, so contract-to-schema agreement is a test, not a convention.

The write path

A fact commits with the sale, or not at all.

Facts are emitted from inside the domain transactions themselves — POS completion, storefront fulfillment, service billing, the daily close, payments, and stock receiving all call the same recordFacts function before their own mutation commits. There is no event bus between the business outcome and its reporting evidence; the two share one commit or neither happens. Cost basis crosses here too: emitters attach a per-unit cost only when the inventory ledger fully knows it. Unknown cost is omitted, never zeroed.

Identity is structural — a five-part index of store, domain, source, line, and kind rather than a concatenated string key, so the escaping bug class is designed out. A replay with an identical fingerprint is a no-op. A replay with different content is not an update: the existing row is quarantined in place, and the fold excludes quarantined facts while counting them in a visible flag. Conflict is preserved as evidence, not resolved by whoever wrote last.

The correctness authority

One pure function is the rebuild, the reconciliation, and the backfill.

foldDay takes a currency, a day’s facts, and an optional close reference, and returns the day’s metrics. It is pure by construction — no database, no clock, no randomness — and order-independent. Because every closed day is written through this one function, recomputing a day, applying a late fact, and backfilling history are the same operation, and idempotency, drift, and ordering stop being three separate problems.

The open day is handled with deliberate modesty. Ingestion patches today’s totals incrementally so the workspace feels live, but that arithmetic intentionally shares no code with the fold, is labelled open, and is wholesale-replaced at the next fold. Imperfect incremental arithmetic is acceptable; a wrong closed day is not.

Honesty survives aggregation. Gross profit is null — not zero — whenever any contributing unit lacks a cost basis, the null propagates up every level, and the uncovered revenue stays visible in its own field. Day status is equally precise: reconciled means a close exists and nothing landed after it — timing, not agreement. A reconciled day can still disagree with its close, the variance is stored, and that row is precisely the one an operator should look at.

The one cron

Liveness is a row in a table, not a chain of scheduled jobs.

All asynchronous work belongs to a single job that sweeps every five minutes. Work arrives as dirty-day rows in their own table — deliberately separate, so marking a day dirty does not invalidate the live subscriptions readers are holding. A crashed sweep leaves its marks for the next tick; there are no wedged states to un-wedge. Delivery is at-least-once by construction: the mark is deleted before the fold runs. A crash after the delete loses nothing, because the fold is idempotent and the next fact re-dirties the day; a crash before it re-runs the fold. Both directions are safe, and double-processing — the direction that is not — cannot happen.

Every read in the sweep is bounded, and the bounds are refusals, not truncations.

The read side

Every query declares its worst case.

The read side is seven queries, each opening with the same access check and each carrying a declared worst-case document budget. The overview — KPI snapshots, comparisons, the thirty-day trend, the trust strip — is denormalized at sweep time into one singleton document per store, so the dashboard costs one read and re-executes at most once per sweep instead of once per fact.

  • Overview dashboard1 document
  • Day-by-day table (92-day span)≤92 documents
  • Item performance page≤36 rollup documents
  • SKU detail trend≤92 documents
  • Per-day transaction evidence≤501 facts + sources

The backend’s indexes are ascending-only, so top-N-by-revenue is stored as a negated sort key and becomes an indexed range read rather than a scan; ties are resolved deterministically in application code from a bounded overfetch rather than trusted to index order. Arbitrary date ranges do not get to break the budgets either: a custom range is a request — a deterministic key and a pending row — that the sweeper computes from derived documents and the client’s subscription picks up when it completes. No polling, and no query whose cost scales with the operator’s date picker.

Access is one function with one answer: every reports query requires the store’s admin role, and every failure mode throws the same opaque message, so a caller cannot distinguish “does not exist” from “exists but you cannot see it.”

The workspace

The URL is the state, and the data holds still while it refreshes.

The workspace — an overview tab, an items tab, and a per-SKU detail page — keeps every meaningful choice in the URL as schema-validated search parameters: window, period, sort, cursor, selected day. A report view is a link you can share, and the back button is the undo. The period keys the UI requests are built by the contract’s own helpers, the same code the sweeper used when writing the rollups, so the client cannot ask for a key the backend never wrote.

One rendering problem earned its own abstraction. The reactive query hook returns undefined on every argument change, not just first load, so a naive skeleton tears the panel down on each date change. A small stale-while-refreshing hook keeps the previous data on screen and reserves skeletons for the only case they are honest: when there is nothing to show yet. The workspace is equally honest about freshness — day totals update first, the overview catches up on the sweep cadence, and the interface says so in words — and where a number invites a question, it links out to the system that can answer it: net sales to the POS transaction list, a closed day to the daily close record.

Second opinions

The verifier is forbidden from agreeing by construction.

A folded day gets an independent second opinion. The verifier recomputes a day’s expected metrics straight from the domain tables under three self-imposed rules: it must not import the fold or the emitters’ mapping code, it must never read the fact ledger, and where possible it reads a different column than the emitters did. Shared metric code would make the two sides agree by construction — exactly the failure a verifier exists to catch. On first contact with real store data it caught two defects every unit test had missed: a currency normalization gap and a class of service revenue billed at the till.

Just as deliberately, the verifier reports what it cannot see. Its blind spots are documented rather than papered over, and one known disagreement — a sign convention on voided sales — is left flagging every affected day on purpose until the convention is reconciled. Full rebuilds go through the same front door: reseeding a store is a resumable phase machine that purges the derived tables and re-emits facts from persisted rows, so bootstrap, backfill, and disaster recovery are one code path. And because the layer is fully derived and writes no domain tables, the rollback story is plain — turn it off, and nothing about the business record changes.

Candid limits

Read-optimized is a set of tradeoffs, written down.

The through-line of the design is a consistent trade: flexibility and self-service recovery are given up for read cost, determinism, and honesty. Refuse rather than guess, precompute rather than query, freeze rather than accrete. Each of those choices has a bill, and it is worth naming where it comes due.

  • Intraday numbers are a preview. The open day’s incremental totals can transiently drift; only the fold’s output is treated as correct.
  • Custom ranges are the least finished surface. A completed range expires by age, not by re-fold, so a late fact inside it is not reflected until the result expires — and the workspace panel that would expose ranges is built and tested but not yet mounted on any route.
  • Refusals end in a human. A day past its fold cap and a quarantined fact both preserve the problem instead of guessing — but neither escalates. The mark waits for someone to notice a counter and raise a constant; quarantined evidence has no triage surface yet.
  • Adding a metric is deliberately expensive. A new metric touches the frozen contract, the schema, the fold, and the overview — and history is only correct after a reseed. The inversion that makes reads cheap is the same one that makes the metric set rigid.
  • The compute is sized for a handful of stores. The data model is per-store everywhere, but the sweep is one job with global per-tick budgets: one store’s backfill spends everyone’s fold budget, and the design has not been priced at a volume where concurrent sales contend on the same day document.
