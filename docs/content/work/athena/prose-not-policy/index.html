Athena technical reflection

Prose, not policy

Athena’s delivery instructions told agents to finish code review before spending the expensive merge gate. That ordering lived in prose, and prose is advisory. This is how it became policy the harness enforces, and what the enforcement got wrong in its first day.

The failure mode

An instruction is not an invariant

Athena’s merge gate is expensive on purpose: it runs everything a release candidate must pass, ending in the repository-wide coverage suite. The workflow said to complete independent code review first, because review findings change the code. But the ordering lived in skill instructions, and agents sometimes entered the heavy gate anyway: a full validation cycle, then a review that requested changes and invalidated the work the gate had just blessed.

The harness could already prove many facts about a candidate: its changed surfaces, documentation state, generated-artifact freshness, tree and base identity. It lacked a first-class way for a gate to require evidence of an earlier judgment-bearing act: proof that this exact candidate had already passed independent review.

The wrong fix

A marker file cannot carry a judgment

The obvious fix is a tracked “review passed” marker, and it fails every way at once. A marker is forgeable, goes stale silently after an edit or rebase, travels to worktrees it was never true in, dirties the very candidate it attests, and cannot say whether review actually passed or a human deliberately chose to proceed without it.

So the design inverts the question. Instead of recording that a step ran, the gate names the truth it needs: a green independent review of this candidate. Providers decide how that truth can be proven.

The obligation model

Gates declare what must be true; providers prove it

A typed registry declares each gate’s obligations; the first gate began with review.green and documentation.current, and has since gained a third, a durable record of what the delivery cost. A pure evaluator resolves each obligation into one of six outcomes: satisfied by evidence, satisfied by a live fact, waived, delegated, not applicable, or blocked. The outcomes are deliberately not interchangeable: a waiver is never presented as passing review, and CI delegation is not review success.

Enforcement lives inside the gate that spends the money. The public validation command routes only through an admission wrapper that evaluates every obligation, records the decision, recaptures the candidate, and directly spawns the heavy commands. There is no check && heavy-command shell tail a caller can skip past.

Not every change owes a review. The obligation activates at fifty changed relevant lines, excluding tests, generated artifacts, and lockfiles, or at any touch of a registered review-sensitive surface, however small. Sensitivity is metadata on the existing surface registry; the evaluator keeps no duplicate list of important paths.

Exact-candidate evidence

Approval binds to the exact tree that was reviewed

Review evidence identifies the complete candidate it approved: the tree being validated, the configured base’s tip, the merge base that scoped the review, and the worktree it happened in. Any edit, rebase, or change of worktree makes the evidence stale rather than arguably still fine. After a fix, the provider prepares the resulting candidate and reviews it again; there is no unreviewed-delta path.

The records are held to the same standard as the policy: Git-private, worktree-scoped, written atomically, never touching the tracked candidate. Manifests are accepted only from approved review workflows at their final green pass; a textual “ready” in an agent’s output cannot authorize a gate.

Caller posture

The same gate treats an agent, a human, and CI differently

The observed failure mode was agents casually skipping workflow ordering, so agents get the strict posture: fresh green review evidence or a block, with no waiver available. An interactive human may deliberately acknowledge the missing review inline; the decision is recorded honestly as a waiver bound to this candidate, never as review having passed. CI may own the obligation only under an explicitly declared policy, and anything unknown fails closed. Positive agent signals outrank terminal interactivity, so an agent holding a PTY does not become human.

The follow-up

The enforcement had ordering bugs of its own

The enforcement merged on August 11, 2026. By the next day, real use had surfaced two ordering defects that made cheap failures expensive. Deterministic lint ran only inside the heavy provider, behind the review obligation, so a lint rule could fail only after a full review had been recorded, and its one-line fix invalidated that review. And because evidence was bound to the raw tree, a commit to delivery documentation, content the deliverable fingerprint already excludes, also invalidated a recorded approval.

The correction moved the cheap checks ahead of the judgment: preparation now runs a mechanical stage first and publishes no receipt when it fails, so a tree that cannot pass a deterministic rule never reaches review at all. Evidence now binds to a deliverable identity, a digest of the tracked tree minus the folders that merely describe the delivery, and records written under an earlier identity are reported as superseded rather than silently blocking.

This is the pattern the agent-ready repository reflection describes from the other side: the fix did not land as a patch and an apology, but as a reordered pipeline with tests asserting that blocking cases start zero heavy commands.

Candid limits

What this defends against — and what it does not

The design targets accidental and casual workflow bypass, which was the observed problem. It does not attempt to defend against a deliberately malicious caller that edits the harness or fabricates local state, and it adds no cryptographic proof that a caller is human.

  • Enforcement guards one gate so far; migrating the rest of the harness into the obligation registry is deliberate future work.
  • A human waiver reduces friction honestly; it is recorded as skipping review, not as passing it.
  • Activation thresholds mean small, non-sensitive changes proceed without review; the threshold is a judgment, not a guarantee.
  • Blocking before the gate saves the validation cycle; it cannot make the review itself infallible.
