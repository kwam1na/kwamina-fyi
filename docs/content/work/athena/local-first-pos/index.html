Local-first point of sale

Why the register records the work before it reports success—and why offline continuity still has boundaries.

The failure mode

A store cannot wait for the network to decide whether the sale happened.

An online-first register makes the cashier’s success depend on a cloud round trip: send the command, wait, update the screen. When connectivity is slow, intermittent, or lying about being available, the cashier loses receipt context, repeats commands, or cannot tell whether the customer has paid. Bolting an offline fallback beside that path just creates a second register with different guarantees.

This is not hypothetical at Wigclub, the store Athena runs. The design brief said it plainly: internet access in the field is not reliable enough to be a dependency during checkout — and the register is fragile at exactly the moment a customer is ready to pay. So offline is the initial posture, not an added mode.

The command boundary

Local evidence exists before cashier success.

On a provisioned, locally authorized register, every cashier event is appended to the durable local record before success returns. Opening a drawer, changing a cart, taking payment, completing a sale, closing out — all start at the same local command boundary, online or not.

Connected and disconnected

One operating path, not an offline fallback.

The same append-first path runs when the network is healthy and when it is gone. Connectivity wakes synchronization, refreshes seed data, validates cloud state — it does not decide whether the cashier’s work is recorded locally first. Cart, payments, receipt context, and register lifecycle all stay recoverable from one event history.

The first release got this wrong — it preferred cloud commands whenever the browser claimed to be online — and was inverted the day after it landed. The fix was to stop trusting that claim entirely: local append is primary in every condition, the cloud is background projection.

Cloud acceptance

Synchronize in order. Reconcile without rewriting history.

When the cloud is reachable, events upload in order through an authenticated terminal boundary. The upload is idempotent — retrying the same evidence cannot mint a second sale — and accepted mappings tie local identifiers to cloud records.

Acceptance is not the only outcome. A stale product reference, changed authority, or conflicting cloud state becomes manager-visible review work; the completed sale is preserved, the receipt never rewritten, the mismatch never hidden.

Strict ordering earned its design by failing. Upload order was originally computed at sync time from events carrying the signed-in cashier’s proof — so when a cashier signed out with unsynced sales, their events dropped out of the upload set, later staff took earlier sequence numbers, and the server correctly held the shifted batch as out-of-order, forever. The fix separated attribution from authority: every event gets a durable upload sequence the moment it is written, and the terminal — not the cashier — owns the drain. A cashier who never returns can no longer strand the store’s records.

The same discipline guards the seams. A data-shaped failure is validated before the first write, so one poison event cannot wedge a register’s stream or commit half a sale. Sales stranded by an earlier policy were repaired by replaying their stored events through the production projection path — never by hand-editing durable records. The test everything here answers to: in an offline cash system, the failure that matters most is money changing hands while the record goes missing or wrong.

Two authorities

Local continuity and cloud truth do different jobs.

The register is authoritative for one thing: whether it durably recorded the cashier’s action. Once upload is accepted, the cloud projection is authoritative for the shared business record. That split lets the store keep selling without treating an unvalidated device as universally trusted.

Local authority

Protect the cashier’s completed timeline

  • Requires terminal, staff, drawer, and durable-storage readiness.
  • Accepts the command into the local event log before success.
  • Preserves cart, payment, transaction, and receipt continuity.

Cloud authority

Project the shared business record

  • Authenticates and validates uploaded terminal events.
  • Maps local identifiers and applies accepted business records.
  • Surfaces conflicts and reconciliation work without erasing local evidence.

Candid limits

Offline-first is a bounded promise.

POS is Athena’s offline-first workflow; the rest of the operating system is not promised offline. Even the register needs a provisioned terminal, a locally authorized staff member, drawer authority, and a healthy durable local destination.

  • Last-known stock can drift. A disconnected register can preserve a sale, but it cannot prove another terminal or channel has not changed inventory.
  • Cloud validation can wait without disappearing. Deferred events remain visible to synchronization and support flows until validation returns.
  • Conflict is evidence, not failure theater. Review work remains explicit rather than being hidden behind an apparently successful sync.
  • Accepted cloud projection becomes the cloud source of truth. Local continuity does not grant a terminal authority over every shared business record.
