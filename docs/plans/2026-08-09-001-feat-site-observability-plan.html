Site observability, without visitor surveillance.

A high-level plan to see who is using the site in aggregate, catch page and chat failures quickly, and diagnose the full request lifecycle—while keeping identity and conversation content out of telemetry.

Why now

Failures should be visible before a visitor has to report them.

Today, important client-side failures can disappear into a local console. This plan establishes a small operating baseline: understand aggregate traffic, spot degraded experiences, trace assistant failures, and confirm production health from outside the system.

Understand

Visits and page health

See aggregate site visits, canonical page views, route distribution, and Core Web Vitals.

Detect

Frontend and service failures

Turn page, chat-render, Worker, and dependency failures into actionable signals.

Prove

Production availability

Use external uptime checks and bounded canaries to catch silent regressions.

Signal coverage

What we will be able to see

Site usage

Aggregate visits and page views across canonical routes.

Page experience

Core Web Vitals and material browser-render failures.

Chat health

Replay, streaming, persistence, and render outcomes without message content.

Worker health

Structured failures and traces across the API boundary.

Dependency health

Where Anthropic or D1 contributes to a failed operation.

Production health

External page, API, and bounded assistant checks.

Operating model

Three surfaces, one clear responsibility each

The plan avoids building a new analytics platform. Each provider handles the signal it is best suited to own.

Cloudflare Web Analytics

Audience and experience

Owns aggregate visits, canonical page views, and Core Web Vitals.

Cloudflare Workers

Server authority

Owns structured logs and traces for API, assistant, and persistence operations.

Sentry

Action and notification

Owns actionable exceptions, release context, and primary uptime monitoring.

Non-negotiable boundary

Observe the system, not the person.

Telemetry is allowlisted, bounded, and fail-open. Losing observability must never break navigation, rendering, chat streaming, or persistence.

What may be collectedCanonical route, release, fixed outcome, timing, safe stack location, and a short-lived operation correlation ID.
What never leaves the product boundaryIdentity, chat content, thread credentials, raw IP or user agent, full URLs, query strings, referrers, request bodies, DOM, and input values.
Delivery shape

Roll out in four controlled phases

Collection comes before dashboards; baselines come before noisy thresholds; every phase must prove privacy and availability.

Foundation

Confirm provider ownership, access, retention, release identity, and privacy defaults.

Collection

Enable page views, performance, browser failures, Worker signals, and safe correlation.

Operations

Create operator views, saved queries, alert routes, and a practical runbook.

Proof

Exercise production canaries, privacy audits, failure drills, and rollback paths.

Finish line

How we know the posture is materially better

  • Site and canonical page visits are visible in production.
  • Page performance and browser crashes are actionable.
  • A chat operation can be followed across the Worker and dependencies.
  • Chat lifecycle states remain distinct without exposing content.
  • External checks catch site, API, and bounded assistant regressions.
  • Alerts reach an owner and recover cleanly after resolution.
  • Forbidden data is absent from provider exports and notifications.
  • Provider failure has no user-visible impact.

Scope boundaries

Now, later, and never

Now

Visits, page performance, errors, Worker/chat lifecycle, dashboards, alerts, synthetics, and runbooks.

Later

Richer product funnels, longer-term trend analysis, and automation—only if a clear need emerges.

Never

Visitor identity, session replay, transcript inspection, prompt analytics, advertising profiles, or behavioral surveillance.
